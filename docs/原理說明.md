## 1. 先搞懂名詞

看不懂術語是卡住的最大原因，先把常出現的字都列出來。

| 名詞 | 白話解釋 |
|---|---|
| **Transaction log（交易日誌）** | SQL Server 背地裡自己寫的一本流水帳，每次新增、修改、刪除資料，都會先記一筆進這本帳，才真的去改資料。這是資料庫防止斷電/當機時資料損毀的機制，關不掉。 |
| **LDF** | 存放 transaction log 的實體檔案（副檔名 .ldf）。 |
| **LSN（Log Sequence Number）** | 流水帳裡每一筆的「編號」，越後面發生的事，編號越大。格式長得像 `0000002D:00000100:0001`，可以直接當文字比大小排順序。 |
| **`fn_dblog()`** | SQL Server 內建的一個函式，可以把 transaction log 裡的內容讀出來給你看。**沒有官方文件**，這是這整個專案最大的風險來源——行為沒人保證、換版本可能會變。 |
| **Row（列）** | 表格裡的一筆資料，例如「Id=1, Salary=50000」這一整筆。 |
| **Page（頁）／Slot（格）** | SQL Server 儲存資料不是一筆一筆散放，是把很多列打包放進一個固定大小（8KB）的「頁」，頁裡面再分成一格一格的「Slot」。**「Page ID + Slot ID」就等於這一列資料的門牌地址**，只要這一列沒有搬家，這個地址不會變。 |
| **Byte（位元組）** | 電腦儲存資料的最小單位，一個 byte 是 0~255 之間的一個數字。所有資料——不管是數字、文字、日期——最終都是一串 bytes。 |
| **Hex（十六進位）** | 因為一長串 0~255 的數字很難讀，習慣上會用兩個字元表示一個 byte（例如 `0A`、`FF`），這就是 hex。你在這個專案的程式碼和對話裡看到的 `E90300` 這種字串，就是 hex。 |
| **Schema（結構描述）** | 一張表格的「說明書」：有哪些欄位、每個欄位是什麼型別（INT、VARCHAR...）、能不能是空的。 |
| **Offset（偏移量）** | 「從頭數過來第幾個 byte」。例如「Salary 欄位的 offset 是 15」意思是這一列的第 15 個 byte 開始，就是 Salary 的資料。 |
| **NULL** | 資料庫裡「沒有值」的意思，跟數字 0 或空字串 `''` 是三種不同的東西。 |
| **DDL（Data Definition Language）** | 改表格結構本身的指令，像 `ALTER TABLE ADD COLUMN`（加欄位）、`ALTER TABLE ALTER COLUMN`（改型別）。跟 DML（新增/修改/刪除資料本身）是不同類別。 |
| **VLF（Virtual Log File）** | Transaction log 檔案內部其實切成很多小段循環使用，每一小段叫 VLF。這個先知道名字就好，跟目前做的功能沒有直接關係（是「離線深度挖掘」那個進階功能才會碰到）。 |

## 2. 整個問題是什麼

一句話：**客戶的資料庫被改壞了、被刪錯了，但客戶事前沒有開任何「誰改了什麼」的記錄功能，我們能不能事後從 transaction log 裡把真相挖出來？**

答案是可以，而且核心賣點就是：transaction log 是關不掉的，所以就算客戶什麼都沒設定，資料本來就已經被記下來了——只是要挖出來、翻譯成人看得懂的樣子，需要做很多工。

## 3. 資料怎麼變成一串 bytes

用最簡單的例子講：一張表 `Employees(Id INT, Salary INT)`，一列資料 `Id=1, Salary=50000`。

SQL Server 實際存的東西，簡化後大概長這樣（每個方括號是幾個 bytes）：

```
[一些固定的旗標資訊，共 4 bytes]  [Id 的值，4 bytes]  [Salary 的值，4 bytes]  [其他附加資訊...]
```

`Id` 存在第 4 個 byte 開始的位置，`Salary` 存在第 8 個 byte 開始的位置——這個「誰存在第幾個 byte」的規則，叫做這張表的 **row layout（列版面）**。

**每一種型別佔的 byte 數量不同**：INT 固定佔 4 bytes；VARCHAR（文字）長度不固定，所以版面裡會另外用一小段「這篇文字從第幾個 byte 到第幾個 byte」的索引來記錄，而不是固定位置。這也是為什麼欄位分兩種：**固定長度欄位**（INT、DATETIME2 這種，長度永遠一樣）跟**變動長度欄位**（VARCHAR 這種，每一列可能不一樣長）。

**NULL 怎麼表示**：列的版面裡有一小段叫 **null bitmap（空值位元圖）**，每個欄位對應其中一個位元（bit），是 1 就代表這欄是 NULL、是 0 就代表有值。

這整套規則，SQL Server 從很早的版本到現在幾乎沒有大改過（因為要保證舊備份可以還原到新版本，這部分被刻意設計成很穩定），這是我們敢投資去搞懂它的原因之一。

## 4. Log 裡到底記了什麼

這是最容易搞混、但也是最重要的一段。**三種操作，log 記的東西完全不一樣：**

### INSERT（新增一列）
Log 直接存**整列完整的 bytes**。所以只要你能挖到這筆 INSERT 記錄，就能 100% 還原這筆資料當初長什麼樣，不需要任何額外資訊。

### DELETE（刪除一列）
一樣存**整列完整的 bytes**（被刪掉之前的樣子）。這代表理論上「誤刪的資料」是最好救的——只要 log 記錄還沒被覆蓋掉，被刪掉的那一整筆資料原封不動躺在裡面。

### UPDATE（修改一列）
**這裡完全不一樣**。SQL Server 不會把改完之後的整列重新存一次，它只記：

> 「從第幾個 byte 開始，原本是這幾個 bytes，現在變成這幾個 bytes」

打個比方：如果一本書只改了第 100 頁的一個錯字，出版社不會把整本書重印一次夾進你的修訂包裡，只會給你一張紙條寫「第 100 頁，第 3 行，『的』改成『得』」。UPDATE 的 log 記錄就是這張紙條，不是整本書。

**這代表什麼**：要還原「改之前」「改之後」的完整樣子，你必須先有一份「改之前完整長什麼樣」的底稿，然後把這張紙條貼上去，才能得到改之後的樣子。這份「底稿」從哪裡來？最乾淨的來源就是這一列當初的 **INSERT 記錄**——這也是為什麼我們的程式要追蹤「這一列從一開始到現在，經歷過哪些操作」，而不能只看單獨一筆 UPDATE 記錄。

**還有一個容易忽略的細節**：改之前跟改之後的紙條，長度可能不一樣長！比如把一個很短的名字改成很長的名字，「改之後」那段自然比較長。所以貼紙條的時候，不能假設「換掉一樣多的字」，要先算清楚「原本這段占幾個 byte、要被拿掉，新的這段占幾個 byte、要被塞進去」，這個動作我們叫它 **splice（拼接）**。如果算錯，會把整列資料悄悄弄壞而且完全不會報錯——這是我們踩過的坑之一。

## 5. 我們怎麼發現這些規則的（方法論）

**沒有文件可以查，這些都是實驗試出來的。** 步驟大概是：

1. **建一張測試表，塞進去自己知道答案的資料**（例如故意插入 `Id=1, Salary=50000`，因為是自己塞的，正確答案 100% 確定）。
2. **用 `fn_dblog()` 把這筆資料在 log 裡的原始 bytes 挖出來**，會得到一長串 hex 字串，第一眼完全看不懂。
3. **肉眼比對**：既然知道答案是 50000，就去那串 hex 裡面找——50000 換算成電腦的表示法應該長什麼樣？結果真的在某個固定位置找到了。換一筆資料再測一次，位置還是一樣，代表這不是巧合，是規律。
4. **交叉驗證**：後來發現 SQL Server 自己有一個系統資料表 `sys.system_internals_partition_columns`，可以直接查出「這個欄位存在第幾個 byte」，拿去跟我們肉眼試出來的結果比對——完全吻合，這時候才真的放心把規則寫成程式，不用每張新表都重新肉眼猜一次。
5. **針對各種邊界情況反覆測試**：NULL 值、文字變長、文字變短、刪除、改主鍵、表格結構被異動……每一種都要重新做一次「插入已知資料 → 挖 log → 比對答案」，確保規則在各種狀況下都成立，不是只在最簡單的情況下碰巧對。

整個實驗過程都是先用 PowerShell 寫成「用完即丟」的腳本在你這台電腦上跑（還留在 `AI 產品規劃\experiments\` 資料夾裡，可以回去看），等規則確定沒問題了，才**重新用 C# 寫一次正式版**，就是現在 LogCarver 這個專案。

## 6. 程式架構：六個檔案在做什麼

用剛才的比喻串起來，每個檔案負責一小段：

| 檔案 | 負責什麼 | 對應到前面哪個概念 |
|---|---|---|
| `SchemaReader.cs` | 問 SQL Server：「這張表每個欄位存在第幾個 byte？」 | 第 3 節：查出 row layout |
| `FnDblogReader.cs` | 去 `fn_dblog()` 挖出這張表所有的 INSERT/UPDATE/DELETE 原始記錄 | 第 4 節：把 log 記錄撈出來 |
| `RowDecoder.cs` | 把一串 bytes 翻譯成「Id=1, Salary=50000」這種人看得懂的樣子 | 第 3 節：bytes → 有意義的值 |
| `RowPatcher.cs` | 把 UPDATE 的「紙條」（差異片段）貼到底稿上，算出改之前/改之後的完整 bytes | 第 4 節：splice 拼接 |
| `RowHistoryReconstructor.cs` | 按照 Page ID + Slot ID（門牌地址）追蹤「同一列資料」從出生到現在的完整歷程，決定每筆 UPDATE 要拿哪一份底稿去貼紙條 | 把前面所有東西串起來 |
| `DdlBoundaryReader.cs` | 找出這張表什麼時候被改過結構（加欄位、改型別），標記出一條時間線 | 第 7 節：防止被舊資料騙 |

## 7. 最危險的陷阱：表格結構改過怎麼辦

假設一張表原本只有 `Id, Salary` 兩個欄位，後來加了一個新欄位 `Bonus`。現在你去查「三個月前的某一筆 UPDATE 記錄」，那時候 `Bonus` 這個欄位根本還不存在。

如果程式笨笨地照現在的版面（三個欄位）去解讀三個月前的 bytes（只有兩個欄位的版面），會發生什麼事？**它會把不屬於 `Bonus` 的某段 bytes，硬解讀成一個 `Bonus` 的數字，而且這個數字看起來完全正常，不會有任何錯誤訊息。** 這是我們在研究階段親手做出來過的真實案例——解出一個看起來合理、其實完全是垃圾的數字。

**這比程式當機還可怕**，因為當機你知道要修，這種情況你完全不會發現答案是錯的。

**我們的解法**：`DdlBoundaryReader` 會先去查這張表「什麼時候被改過結構」，畫出一條時間線。任何一筆記錄，只要它的時間比某次結構變更還早，就直接**拒絕解讀**、誠實告訴你「這筆看不懂，因為它可能是舊版面」，而不是硬猜一個答案給你。這個「沒把握就拒絕，不要亂猜」的原則，貫穿整個專案的設計。

## 8. 目前做到哪、還缺什麼

**已經能做到**：接上一個真的在跑的 SQL Server、指定一張表、給一個時間範圍，列出那段期間所有的新增/修改（含改之前改之後）/刪除，而且對「表格結構被改過」這個陷阱有防護，全部用真實資料庫驗證過、不是紙上談兵。

**還沒做的**：
- 這台伺服器已經關機、離線的情況下，直接讀取 LDF 檔案本身（這是原本研究裡「救回 fn_dblog 看不到的資料」那個真正的差異化賣點，目前的版本還沒碰）
- 表格有壓縮、有大型文字欄位（LOB）、有加密（TDE）的情況——這些都各自需要另一套解讀方式，目前會直接告訴你「這個看不懂」，不會硬解
- 舊版本 SQL Server（2012/2016）還沒有實測過，程式會在偵測到未驗證版本時警告你
